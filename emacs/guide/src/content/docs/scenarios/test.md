**상황**: 서비스 로직을 고쳤다. 관련 테스트만 빠르게 돌려서 확인하고 싶다.

자작 Gradle 러너(`jy-gradle.el`)가 IntelliJ의 test runner를 대체한다. 멀티모듈 프로젝트에서 **모듈 경로(`:app:core`), 클래스 FQN, 커서 위치의 메서드 이름을 자동 감지**해서 `./gradlew :app:core:test --tests 'FQN.method'`를 실행한다. Java/Kotlin 모두 지원하고, Kotlin의 백틱 테스트 이름(`` fun `주문이 없으면 예외`() ``)도 잡는다.

## 실행 키

테스트 파일을 열고 커서를 올려놓은 뒤:

| 키 | 범위 | IntelliJ |
|---|---|---|
| `C-c g t` | 커서가 있는 테스트 **메서드** 하나 | `Ctrl+Shift+R` |
| `C-c g c` | 현재 **클래스** 전체 | |
| `C-c g m` | 현재 **모듈** 전체 | |
| `C-c g r` | **마지막 명령 재실행** | `Ctrl+R` |

`C-c g r`이 제일 자주 쓰인다: 소스를 고치고 → 저장하고 → 어느 버퍼에서든 `C-c g r`로 방금 그 테스트를 다시 돌리는 루프.

## 결과 보기

실행하면 `*gradle: 프로젝트명*` compilation 버퍼가 뜬다.

- **실패 시**: 스택트레이스가 파싱되어 있다. `M-g n` / `M-g p`로 실패 지점 사이를 점프하면 해당 소스 라인으로 바로 이동한다. compilation 버퍼 안에서 파일:라인 위에 `RET`을 쳐도 된다.
- 컴파일 에러(kotlinc `e:` 라인 포함)도 같은 방식으로 점프된다.
- 출력 버퍼는 `C-x 1`로 닫거나 `C-x o`로 오간다.

## 자주 겪는 것

- **"메서드를 감지하지 못했다"**: 커서가 메서드 본문 **안**에 있어야 한다. 클래스 레벨이나 애너테이션 줄에 커서가 있으면 실패한다. 그럴 땐 `C-c g c`로 클래스 전체를 돌리면 된다.
- **"gradlew를 찾을 수 없다"**: Gradle 프로젝트 루트 밖의 파일이다. 프로젝트 안 파일에서 실행해야 한다.
- Gradle 데몬 첫 기동은 느리다. 두 번째부터 빨라진다.
